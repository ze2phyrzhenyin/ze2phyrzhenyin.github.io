From storyboard to delivery

  1. Write down the delivery requirements

    Note the running time, frame rate, aspect ratio and audio requirements. If the 3D source files are to be delivered, also agree on the software version and on how external assets are packed.

  2. Sketch out the main shots

    Give each shot one line stating its start and end frames, the subject’s movement and the camera’s movement. Put the product dimensions, reference images and logo files in the asset list.

  3. Test the hardest section

    Take the hardest 3 to 5 seconds and make a sample. Check outlines and occlusion on a clay render, and reflections in Material Preview. Record the render time for one frame and the peak VRAM.

  4. Output frame by frame

    Render each shot as consecutively numbered images. After a failure, render the missing frames again, and keep the project’s frame rate when assembling. Check subtitle line breaks and audio cut points in the final aspect ratio.

  5. Review and deliver

    Watch the whole video once, looking for flicker, meshes passing through each other and the loudness after each cut. Open the source project from another folder and check the textures, fonts, asset licences and output settings.

Assemble the sample file’s image sequence into an MP4

In Blender, choose Render Animation. A frames folder appears next to the file. Run the command below from the folder that contains the file.

ffmpeg -framerate 24 -start_number 1 -i frames/twin-%04d.png -c:v libx264 -pix_fmt yuv420p twin.mp4

Dividing work between Claude models

When several shots have to be planned at once or a render error tracked down, Opus can break the work down. Once the template is settled, swapping subtitles, changing parameters and tidying scripts can go to Sonnet. Try one shot first, then choose the model from the measured time and usage.

Developer-kit prompt

Write this shoot’s conditions at the top of the prompt and hand it to Claude together with the storyboard, assets, and render and delivery requirements.

Read the full prompt
You are a technical director for 3D video production, a Claude Code architect, a VFX director and a strict quality reviewer.

Goal: build an extensible, runnable, reusable “3D video developer kit”. For every future video request it must identify the objective by itself, then verify and select the production route, tools, Skills, MCP servers, open-source frameworks, generation services, assets and rendering method that actually fit. Do not assume that every project has to use Blender, and do not adopt a tool because it is new and popular.

I. Requirements and constraints
Extract the content goal, style, reference frames, required accuracy of the subject, number of shots, duration, FPS, resolution, whether an editable 3D project is needed, subtitle language, audio, budget, hardware, delivery standard and licensing requirements. Where an item is missing, proceed with a cautious default and list these defaults separately.

II. External research and credibility
Actually search official documentation, GitHub, source code, maintenance status, licences and examples. Compare the options that fit today, such as Blender, MCP, Skills, Cinema 4D, Unreal, Remotion, HyperFrames, Three.js, Runway, Flow, Kling and Meshy, and stay open to finding a newer, better option.
Label each of these separately: capabilities confirmed by official sources, demos described by their authors, unverified projects, and your own inferences. Do not pass off a still frame as a complete animation, and do not claim “cinematic quality” without evidence.

III. Selection matrix
Compare the candidates on at least these criteria: how much of a real 3D project is kept, visual ceiling, control over revisions, batch capability, software and hardware cost, external API fees, learning difficulty, licence restrictions and reproducibility of the project. Give a primary route, a fallback, and the reasons for rejecting the other routes. Each project has at most one main timeline and one main scene writer, so that concurrent agents do not compete for resources.

IV. Architecture and modules
Build the modules below and define inputs, outputs, error handling and tests for each one:
1 requirements: input parsing, quality and budget constraints;
2 research: discovery of tools, Skills and frameworks, verification against official sources, caching and update checks;
3 planner: route scoring, storyboard and asset list;
4 assets: models, textures, fonts, HDRI, audio, licence records;
5 scenes: adapters for Blender Python, Three.js / R3F, Unreal / C4D or generated video;
6 render: per-shot previews, render queue, resuming after interruption, image sequences, FFmpeg assembly;
7 visual-qa: keyframe screenshots, shot comparison, checks of geometry and brand accuracy, detection of flicker, intersecting meshes and cropping;
8 delivery: MP4, source code, editable project, dependencies, origin of models and resources, operating instructions;
9 accounting: Claude subscription, Anthropic API, third-party credits and render time, each recorded separately.

V. Workflow
Confirm the hardware and the available tools first. Blind installs and dangerous scripts are not allowed. Start with the hardest shot of 3 to 5 seconds: actually output the images and read them back, point out the problems and fix them. Extend to the full film once the quality baseline is reached. The orchestration must support persistent task state, retry on failure, staged checks, caching, deterministic random numbers and animation that is deterministic frame by frame. Multiple agents, Skills, tool calls and task graphs may be used, but only where responsibilities are clear and the benefit can be measured.

VI. Image quality standard
Research and apply professional assets, PBR materials, area lights / HDRI, real-world scale, camera language, motion pacing, depth of field, colour management, compositing in post, and the transitions between sound effects and music. Verify every key shot of the actual render with visible evidence. If you cannot look at the image, mark the shot as not passed and do not claim it is done. Refuse empty adjectives such as “cinematic” and replace them with picture requirements that can be checked.

VII. Quotas and safety
Keep these apart: session usage on a Claude subscription, API token costs, costs of other video models, GPU rendering resources and asset licences. Do not convert a 20-second video directly into a fixed Claude percentage. Do not invent a subscription quota that is unknown. Before any purchase or payment, installation of high-risk software, execution of unfamiliar code or upload of private assets to an outside service, explain what is involved and obtain permission.

VIII. Delivery and ongoing maintenance
Provide a code repository that really runs, a README, an example project, a command-line entry point, sample configuration, a dependency lock file, Smoke Tests, quality checks, troubleshooting notes, version control and a rollback method. Produce at least one test clip of 12 to 20 seconds, and supply the MP4, the source code, sample screenshots and the actual time taken. Summarise each run as reusable lessons, and allow the engine, model or Skill to be replaced.

IX. Execution standard
Do not stop at design documents. As far as the environment allows, actually create the files, run the tests, output representative frames and produce the clip. Any step that cannot be run must be stated explicitly in the delivery report. Results must not be fabricated.

Now start by checking the runtime environment, defining the minimum runnable product and verifying the tools and the existing open-source projects. List your selection, then implement immediately.
